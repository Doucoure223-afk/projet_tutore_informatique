Étude de Cas : Anatomie d'une Attaque par Tautologie
Cette étude de cas montre clairement comment une requête SQL vulnérable peut être détournée par une injection de type tautologie. Dans le premier exemple, l’application vérifie normalement les identifiants saisis. Mais dans le second, l’ajout de l’expression OR 1=1 rend la condition toujours vraie et permet de contourner l’authentification. Ce scénario illustre la simplicité et la gravité d’une attaque par injection SQL : une seule ligne mal protégée suffit à compromettre la sécurité. La leçon à retenir est qu’il est indispensable d’utiliser des requêtes préparées et des mécanismes de validation pour éviter que des données utilisateur ne soient interprétées comme du code.

Classification et Taxonomie des Injections SQL
In-Band SQLi (Classique) : L'attaquant utilise le même canal de communication pour lancer l'attaque et récupérer les résultats.
Union-based: Utilise l'opérateur UNION pour fusionner les résultats de la
requête légitime avec une requête malveillante.
Error-based :Exploite les messages 'erreur du SGBD pour obtenir des informations sur la structure de la base.
Inferential SQLi (Blind / Aveugle) :  Aucune donnée n'est transférée directement. L'attaquant reconstruit la base en posant des questions "Vrai/Faux".
Boolean-based :Analyse la différence de contenu dans la réponse HTTP.
Time-based :Analyse les délais de réponse (ex: WAITFORDELAY ou SLEEP())
Out-of-Band SQLi :Utilisation de protocoles externes (DNS, HTTP) pour exfiltrer les données si le canal direct est filtré.

Limites des Mécanismes de Défense Conventionnels
Signatures Statiques (WAF classiques) : Incapacité structurelle à détecter les menaces « Zero-day » (attaques inédites non répertoriées).
Techniques d’Évasion et d’Obfuscation : Contournement facile des filtres par l'utilisation d'encodages (Hexadécimal, URL encoding) ou de commentaires SQL, imbriqués.
Le Dilemme de la Précision :
Faux Positifs: Blocage des requête légitimes( ex: noms contenant une apostrophe: N’DIAYE, N’DAOU, N’GOLO ), nuisant à l’expérience utilisateur.
Faux Négatifs : Fuite de sécurité laissant passer des payloads sophistiqués.
Complexité de maintenance: Nécessité d'une mise à jour constante des bases de signatures face à l'évolution rapide des payloads.
Latence de Traitement : Dégradation des performances lors de l'analyse de règles de filtrage trop denses.

Logigramme de Décision et Gestion de la Zone Grise
Règle de décision hybride : score_ajusté ≥ 80 → BLOQUER ; 30 ≤ score_ajusté < 80 → DÉLÉGUER À IA ; score_ajusté < 30 → AUTORISER.
Pondérations par contexte : login=1.3, admin=1.5, search=1.1.
Exemple chiffré (mini-cas) :
URL: https://mon-app.ml/login?user=admin' UNION SELECT 1,2,3–
pattern 'UNION' (+40) + caractère spécial (+25) + entropie (+20) => score brut = 85 → score_ajusté (contexte login=1.3) = 85 * 1.3 = 110.5 → DÉCISION = BLOQUER.

Features Engineering (𝜙(𝑹)) : Extraction de 11 caractéristiques discriminantes :
Syntaxiques: Présence de ‘, --, ;, /*.
Sémantiques : Mots-clés SQL( UNION, SELECT, OR, SLEEP).
Statistiques :  Longueur de la requête et taux de caractères spéciaux.
Architecture du Réseau (MLP) :
Couche d'entrée : 11 neurones (un par feature).
Couches cachées : Architecture dense ( ex: 11 x 64 x 32).
Fonctions d'activation : ReLU pour les couches internes, Sigmoid pour la sortie.
Optimisation : Utilisation de l'algorithme Adam et de la fonction de perte Binary Cross-Entropy.
